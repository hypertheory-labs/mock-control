# Revisit pumice: MSW 3, before the first publish

The first revisit. It uses `revisits:`, which no format plan defines yet; one in aide
will, from how this goes. Vellum pinned `msw@2` inside a `Chose:` to get past a broken
install step. That quietly re-decided something that belongs to pumice's ground, so
this plan stands where pumice stood and asks the question properly.

## Decision: What moved is our understanding, not the world
- where: `projects/mock-control/README.md › mock-control › Requirements`
- quote: `- Angular 22, with MSW 2.`

**Because (measured):** MSW 3.0.0 was published on 2026-09-28, a month before pumice.
"MSW 2" was already stale when pumice wrote the README; the workspace happened to have
2.15. No pumice entry decided it, so this anchors where the assumption shows, not to an
entry. That's a gap in pumice, found by revisiting it.

## Decision: Ask it in pumice's frame: what's cheapest before the first publish
- where: `` plans/2026-10-29-pumice.md › Selectors use the library's prefix, `mock-panel` ``

**Because (pumice, Jeff):** pumice renamed the selectors because "a rename is cheapest
before the first publish." A peer range is the same kind of promise: widening it later is
easy, but publishing one that excludes npm's `latest` makes every new install fail the
way vellum's did.

## Decision: Measure both versions, the same three ways
- where: `projects/mock-control/package.json › peerDependencies › msw`
- quote: `"msw": "^2.15.0"`

**Because (Claude, not asked):** the library has no tests, so "works" has to be measured
from outside. For MSW 2.15 and 3: the library builds against it; a fresh app following
the README compiles; and in headless Chromium, a mocked endpoint answers with the mock and
a pass-through endpoint is logged as `passthrough`. The pass-through check matters most:
the library detects it by MSW's internal `x-msw-intention` header, which still exists in
3 but is the most likely thing to break quietly.

## Decision: If both pass, support both; if 3 fails, stay on 2 and say why
**Because (Claude, not asked):** supporting both keeps the class apps working on 2 while a
new install gets 3. The one known difference is the start option (`onUnhandledRequest` in
2, `onUnhandledFrame` in 3), which the README can say in a line. If 3 fails, the README
explains the pin instead of just making it.

## Decline: Re-measuring the known limits on MSW 3
- where: `projects/mock-control/README.md › mock-control › Known limits (measured, msw 2.15, Chrome)`

**Because (Claude, not asked):** client aborts and a long-hidden tab need real browser
sessions, minutes long. The section's heading already says what it was measured on, so
it stays true. Re-measuring is its own round if it matters.

## Guess: The library works on MSW 3 unchanged
**Disproved if:** the library fails to build against 3, or either runtime check fails.
